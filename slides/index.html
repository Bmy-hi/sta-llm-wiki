FPGA 靜態時序分析（STA）入門：看懂 setup、hold、slack 與 Vivado 時序報告

← → 或空白鍵翻頁

為什麼需要 STA？

模擬只檢查「你給的輸入」；STA 不跑模擬，把每一條暫存器到暫存器的路徑延遲加起來，檢查每一條都來得及。

  • 每條路徑都做兩種檢查：setup（用最大延遲）與 hold（用最小延遲）
  • 前提：你要先用 create_clock 告訴工具時脈多快
  • Vivado 實作完一定會產生的報告：Timing Summary

Setup 與 Hold：正反器的兩條規矩

Setup time：上升緣之前，D 要先穩定 tSU。看最慢的路徑。
Hold time：上升緣之後，D 要再維持 tH（常常是 0）。看最快的路徑。

違反任一個 → 可能 metastability：輸出卡在中間電位很久才穩定。

一條 Timing Path 長什麼樣子

  • launch 時脈路徑 → 資料路徑（tCO + 組合邏輯）→ capture 時脈路徑
  • skew = 目的端時脈延遲 − 來源端時脈延遲

Slack：你還剩多少時間？

Setup slack = required − arrival = T − datapath(max) + skew − uncertainty − tSU Hold slack = arrival − required = datapath(min) − skew − uncertainty − tH
  • slack ≥ 0 → 過；slack < 0 → 違規
  • 同一個時脈：setup 的要求是一個週期，hold 的要求是 0

算一題：50 MHz 跑得動嗎？

T = 20 ns（50 MHz）、tCO = 2 ns、tPD(max) = 15 ns、要求 tSU = 5 ns

可用 setup 時間 = 20 − 2 − 15 = 3 ns slack = 3 − 5 = −2 ns → 不過！ 最小週期 = 2 + 15 + 5 = 22 ns fmax = 1000 / 22 ≈ 45.45 MHz

要嘛降到約 45 MHz，要嘛把 15 ns 的組合邏輯變短。

看工具怎麼算（setup）

T = 10 ns，來源端時脈延遲 2.0、datapath(max) 7.2、目的端時脈延遲 1.8、uncertainty 0.1、tSU 0.05

arrival0 + 2.0 + 7.2= 9.2 ns
required10 + 1.8 − 0.1 − 0.05= 11.65 ns
slack11.65 − 9.2= +2.45 ns ✔

用簡化式驗算：10 − 7.2 + (−0.2) − 0.1 − 0.05 = 2.45 ns，一致。

Hold：快也是一種錯

來源端時脈延遲 1.9、datapath(min) 0.3、目的端時脈延遲 2.1、uncertainty 0.05、tH 0.1

arrival = 1.9 + 0.3 = 2.2 ns required = 2.1 + 0.05 + 0.1 = 2.25 ns slack = 2.2 − 2.25 = −0.05 ns
兇手是 skew = 2.1 − 1.9 = +0.2 ns：capture 端時脈晚到，資料卻太早變。
正 skew 幫 setup、害 hold。

看懂 Vivado Timing Summary

指標意思過的條件
WNSsetup 最差的 slack（可以是正的！）≥ 0
TNS每個終點的 setup 違規值加總= 0
WHShold 最差的 slack≥ 0
THS每個終點的 hold 違規值加總= 0

例：三個終點 slack = −0.3、−0.1、+0.5 → WNS = −0.3，TNS = −0.4 ns（正的不算）

先把時脈告訴工具：create_clock

# 100 MHz、50% duty 的板子時脈 create_clock -name sys_clk -period 10 [get_ports clk] # 用暫存器 REGA 除 2 得到的時脈 create_generated_clock -name clkdiv2 -source [get_ports clk] \ -divide_by 2 [get_pins REGA/Q]
  • period 單位是 ns：100 MHz ↔ 10 ns
  • 除頻出來的時脈用 generated clock，不要再給 period
  • 差動時脈只在正端定義

修 Setup：讓路徑變短

  • 主因通常是 datapath delay（邏輯層數太多）
  • Pipelining：把長路徑切兩段，越早規劃越好
  • Retiming：把暫存器移到邏輯多的那一段，平衡各段
  • 降頻也能過，但那是「放寬要求」，不是修好
剛剛 15 ns 的路徑切成 8 + 7：最慢一段 slack = 20 − 2 − 8 − 5 = +5 ns，代價是多 1 個週期 latency。

修 Hold：讓路徑變慢一點

  • 主因通常是 clock skew
  • 小違規：router 繞線自動修
  • 大違規（約 > 0.4 ns）：佈線前插入 LUT1 延遲（前提：setup 還有餘裕）
  • 降頻修不了 hold——hold 式子裡沒有 T
剛剛 −0.05 ns 的路徑插入 0.2 ns 延遲：0.5 − 0.2 − 0.05 − 0.1 = +0.15 ns

重點整理

  1. STA 不跑模擬，檢查每一條路徑的 setup（最慢）與 hold（最快）。
  2. slack = 要求與到達的差，≥ 0 才算過。
  3. 正 skew 幫 setup、害 hold。
  4. 報告看 WNS / WHS ≥ 0、TNS / THS = 0。
  5. setup 不過 → 縮短路徑；hold 不過 → 加延遲；降頻只救得了 setup。

小測驗（點開看答案）

Q1. WNS = +0.8 ns、WHS = −0.2 ns，這個設計過了嗎？

沒過。setup 過了，但 hold 有違規（WHS < 0）。

Q2. hold 違規時，把時脈從 100 MHz 降到 50 MHz 有用嗎？

沒用。hold 條件裡沒有週期 T，降頻不會改變 hold slack。

Q3. T = 10 ns、tCO = 1、tPD = 8.5、tSU = 0.3，setup slack？

10 − 1 − 8.5 − 0.3 = 0.2 ns，過。

Q4. 三個終點 setup slack = −0.5、−0.2、+1.0，TNS？

TNS = −0.5 + (−0.2) = −0.7 ns。
